# 弈境用户体验优化与升级规划

评估日期：2026-10-13

评估基线：v1.1.0，Git 提交 `ff29280`

文档状态：保留 v1.1.0 的历史评估与验收标准。下述“当前”“尚未实现”均指评估基线；规划的三个阶段已合并实施并发布为 [v1.3.0](https://github.com/GodBook/yijing-chess/releases/tag/v1.3.0)。实际验证见[执行与验收记录](执行记录.md)，面向用户的说明见[v1.3.0 更新说明](releases/v1.3.0.md)。更强外部引擎仍按 P2-04 的评测前提后续决定。

## 1. 优先方向

建议下一轮升级先解决“棋局能可靠继续、棋谱与棋盘一致、AI 和胜负判定可信”，随后改善手机上的操作和阅读体验，最后完善复盘与学习功能。

项目已经具备三种棋类、本地 AI、双人同屏、摆谱和在线更新的基础。当前更值得投入的是把这些功能串成完整流程：从进入一盘棋，到中断恢复，再到终局、保存和复盘，每一步都应符合用户预期。

本次参考 `redesign-existing-projects` 的界面与交互审查方法，重点检查入口层级、操作反馈、状态完整性和适配问题，并结合规则、存储与更新代码核验。评估包含源码检查、现有规则测试以及对现有编译产物的 JVM 诊断；未进行安装、真机界面操作或视觉截图验收。文中“已确认”指源码或 JVM 结果支持的结论；小屏裁切、字号观感和性能耗时仍需设备验证。

## 2. 当前能力与实际边界

| 模块 | 当前已实现 | 仍待完善 |
| --- | --- | --- |

## 3. 第一优先级：修复核心体验

优先级定义：P0 为影响棋局、棋谱或结果可信度的问题；P1 为高频操作、适配和功能完整性改进；P2 为后续产品增强。以下编号可直接作为开发任务编号。

### P0-01：真正实现“一键继续”，统一离开棋盘的流程

已确认的问题：

- 大厅“继续象棋／围棋／国际象棋”仅传递棋类与模式，进入页面后仍创建初始棋盘。用户还要寻找顶部恢复图标，再操作一次。
- 页面 `attemptExit()` 与 `MainActivity.requestTabSwitch()` 都负责保存确认。页面确认保存后调用返回，父级仍认为棋局活跃，存在再次弹出保存确认的调用路径。
- 页面选择“不保存”会删除该棋类已有存档，底部导航选择“不保存”则保留旧档，两处语义不同。
- 恢复函数没有接续 AI 轮次。若在 AI 应走时保存，恢复后不会自动开始搜索，棋盘点击也没有单独限制用户操作 AI 阵营。

升级方案：区分“新开棋局”“恢复指定棋局”“编辑草稿”三种进入意图。大厅继续按钮传递存档标识，加载成功后直接显示原局面、轮次、难度和历史；恢复到 AI 回合时重新发起一次搜索。离开棋盘由统一入口处理，顶部返回、系统返回和底部导航共享同一逻辑。

验收标准：三种棋类均可一次点击恢复；返回或切换最多出现一次确认；取消留在原局面；“放弃本次未保存修改”保留此前存档，“删除存档”作为独立操作；AI 回合恢复后只落一手，用户无法代走 AI。

源码依据：`HomeScreen.onNavigateToGame`、`MainActivity.requestTabSwitch`、三个棋盘页面的 `attemptExit` 与 `restoreSavedGame`。

### P0-02：自动保存完整棋局，保护摆谱草稿

已确认的问题：棋盘和历史主要保存在页面 `remember` 状态中，持久化只在显式保存时触发。系统回收进程等场景没有可靠的最近棋局恢复路径；摆谱模式被排除在“活跃棋局”之外，未保存的摆谱修改也没有退出保护。

当前存档只保存局面、轮次、难度、着法列表和围棋提子数。恢复时清空 `boardHistory`，所以恢复后不能撤销保存前的走步；围棋的劫点、连续停着次数没有保存；国际象棋 `fromFen()` 没有恢复半回合计数和完整回合数，`applyMove()` 也没有维护这些计数。

升级方案：

- 每次有效走子、停着、悔棋及编辑草稿变更后，顺序写入最新状态；进入后台时补存，避免仅依赖退出弹窗。
- 保存起始局面、当前局面、真实行棋方、规则状态、对局结果、当前历史位置及模式配置。将“落子”和“停着”建模为不同事件。
- 使用 ViewModel 管理会话，用持久化快照恢复进程回收后的棋局；通过起始局面与事件重建可撤销历史，必要时设置检查点。
- 存档加入 `schemaVersion` 和显式校验结果，区分“无存档”“损坏”“版本不兼容”。保存失败时保留当前棋局并提供重试。
- 编辑草稿与正式对局分开保存，显示“草稿已保存／保存失败”，避免编辑覆盖对弈记录。

验收标准：后台回收后恢复到最后一次成功持久化的操作；劫争和停着状态保持一致；新格式存档恢复后可悔棋；旧档迁移不改变已有棋子位置。旧档缺少起始局面或停着信息时保留当前局面并说明历史恢复边界，不补造丢失的规则状态。

### P0-03：让棋盘、悔棋、恢复与导出使用同一份历史

已确认的问题：三个页面分别维护 `boardHistory`、`moveHistory` 和 `MoveTreeNode`。走子会追加树节点，但悔棋没有把树游标回退，重开没有重建根节点，恢复也没有重建着法树。导出却读取着法树，因此会出现：

- 悔棋后，导出仍包含被撤销的走步。
- 重开后，旧对局与新走步串在同一棵树中。
- 从新页面恢复存档后，棋盘有棋、着法列表有记录，导出的树仍可能为空。
- `fenBefore` 字段实际在走子后赋值，未来复盘会把走前、走后局面混淆。
- 围棋双方停着均没有写入历史或着法树，悔棋和 SGF 无法准确还原整盘棋。

升级方案：以“起始局面＋事件历史＋当前游标”为统一来源；棋盘、走步列表、悔棋、复盘与导出都从该状态生成。重开建立新的对局标识和根节点，摆谱开局记录自定义起始局面。围棋停着作为真实回合进入历史，并按 SGF 输出 `B[]`／`W[]`。

验收标准：走四手后撤销两手，导出主线只包含当前保留的两手；若保留分支，撤销内容只能作为明确分支存在。重开后导出为空的新对局；保存恢复前后的棋谱主线一致；含停着的 SGF 可以还原行棋顺序与终局条件。

### P0-04：修复 AI 的评分视角，先验证棋力再增加难度

已确认的问题：象棋与国际象棋搜索递归使用 Negamax 的逐层取负方式，但叶节点和静态搜索始终按固定的 `maximizingSide` 估值，终局分数也采用固定阵营视角。两种评分约定混用，会影响不同搜索深度下的决策。

JVM 诊断使用国际象棋局面 `7k/8/8/3r4/3Q4/8/8/K7 w - - 0 1`：白方可以走 `Qxd5` 吃掉无保护黑车，中级 AI 实际选择 `Qg7+`，随后黑王合法走法中包含 `Kxg7`，可以直接吃掉白后。该局面叶节点在白方、黑方行棋时都返回 `400`，与递归逐层取负的约定不一致。中国象棋存在同构实现，需同步检查与修复。

升级方案：统一采用当前行棋方视角的 Negamax，或完整采用固定阵营视角的 Minimax。将普通估值、将死分数、静态搜索与剪枝边界一起调整。静态搜索遇到被将军时应搜索应将走法，不能直接以静态局面作为可接受结果。加入固定局面回归，覆盖吃无保护大子、避免一步送子、一步／两步杀棋及深度奇偶变化。

验收标准：上述局面不再选择可被立即吃后的 `Qg7+`，并能识别安全吃车；红黑／黑白对称局面评价方向一致；更高难度通过同一组战术用例。难度名称和宣传以验证结果为准。

### P0-05：统一终局状态，正确处理停着与胜负

已确认的问题：

- 国际象棋 AI 无合法走法时直接提示“白方胜”，没有区分将死和困毙；双人模式及玩家无合法走法时也缺少完整终局流程。
- 中国象棋部分路径只在“无合法走法且被将军”时结束，遗漏困毙判负；关闭胜负弹窗会清除 `checkmateWinner`，终局状态依赖弹窗是否存在。
- 围棋连续停着后只显示 Toast，棋盘仍可操作，没有数子、结果确认和争议后继续下棋的流程。
- 已定义的 `GameStatus` 尚未成为三个页面共同使用的对局状态。

升级方案：独立保存进行中、待结算和已结束状态；AI 思考作为单独任务状态。每次走步、停着、悔棋、恢复后统一计算对局状态。关闭结果弹窗只隐藏展示，不改变结果。

验收标准：中国象棋将死／困毙均正确判负；国际象棋将死判胜、困毙判和；围棋两次连续停着后停止普通落子并进入待结算状态。已结束棋局可保存、导出、复盘或再开一盘。围棋先提供明确的待结算与协商结果流程，再完善规则选择、贴目、死子标记和数子；其他和棋规则按实际支持范围明示。

### 4.1 大厅：让开始和继续更容易找到

当前大厅的标志、标语、检查更新和三个介绍卡片占据较多空间，每个棋类又放置三个并列操作，主要文案偏引擎实现细节。

建议首屏顺序为“最近棋局／继续对局 → 选择棋类 → 开始新局”。最近棋局展示棋类、模式、难度、手数、更新时间和缩略局面；无存档时展示简洁的开始入口。棋类介绍改为用户可理解的信息，例如“支持双人、人机和残局摆谱”，规则与引擎细节放入说明页。版本号读取 `BuildConfig.VERSION_NAME`，更新入口放入设置／关于，下载状态保留可见入口。

对局前用一个轻量设置面板集中选择模式、执子方、难度、围棋路数；记住上次偏好。保留现有底部棋类导航，减少在棋盘上反复排列相同选项。

### 4.2 棋盘：优先保证落子准确和状态明确

- 主操作区固定提供悔棋、提示和更多；翻转、导出、摆谱、重开放入可发现的更多菜单，降低当前横向滚动栏的查找成本。围棋目前 `onFlip = {}`，应实现翻转或隐藏该项。
- 新增可收起的走步列表，显示当前手数；点击历史进入明确的查看模式，返回当前局面后继续走子。
- 象棋绘制位置与点击换算采用不同的网格公式，应统一为同一套坐标变换，并验证翻转前后、边缘和交叉点附近的命中。
- 围棋目前点击直接落子，且盘外位置会被钳制到边缘格点。19 路小屏建议提供可关闭的落点预览、拖动定位或局部放大，超出有效区域时不落子。
- 稳定状态栏高度的同时允许大字体自适应；“将军”“AI 思考”“保存失败”使用文字和形状反馈，避免只靠颜色区分。
- 普通按钮建议至少具有 48dp 触控范围；密集棋盘格点通过放大或替代操作提升可达性，不把每个围棋点强行扩成重叠按钮。

### 4.3 棋谱：先保证准确，再扩展格式

PGN 当前缺少自定义起始局面的 `SetUp`／`FEN` 标签，结果默认 `*`；SAN 记谱缺少同类棋子的消歧和将死 `#`，骑士升变还会输出 `=K`，应输出 `=N`。这些问题应与 P0-03 同步处理，文件分享在准确性验收后开放。

SGF 目前按节点手数奇偶推定黑白，并从根节点的第一个子节点开始导出；需改为记录真实行棋方，正确处理选中主线、分支、停着、摆谱的 `AB`／`AW`／`PL` 和规则元数据。现有 `parseSimpleSgf()` 只提取两个字母的坐标，丢失颜色、停着与结构，也未接入页面，不能直接作为完整导入器使用。

国际象棋 PGN 与围棋 SGF 应使用独立阅读器做往返验证。中国象棋 PGN／FEN 需写明支持的具体记谱约定和目标工具；中国象棋 SGF 如计划支持，应作为独立格式任务定义，避免直接复用声明 `GM[1]` 的围棋格式。

### 4.4 更新：让“后台下载”和“重试”符合实际行为

更新管理器及下载协程目前属于大厅页面；“后台下载”只把状态设为 Idle，下一次进度回调仍会修改状态，重新显示弹窗；离开大厅又会失去页面协程及更新管理器，无法保证真正持续的后台任务。下载失败后的重试当前只重新检查版本。

建议使用应用范围的更新状态与 Android DownloadManager 等系统下载机制，关闭弹窗后通过状态入口查看进度。未知下载大小显示不定进度；取消、下载重试、安装重试各有明确行为。检查更新失败保留具体原因，404 或 Release 没有 APK 不显示“已是最新版本”。首次安装时检查本应用的安装授权，授权返回后继续原流程。安装前校验包名、版本、签名兼容性及下载完整性；有可信发布摘要时校验摘要。

## 7. 实现与发布配套

### 7.1 状态与存储

继续使用 Kotlin 与 Jetpack Compose。把三个页面中重复的保存、退出、任务取消和历史管理抽到共享会话层；各棋类保留独立规则引擎和棋盘渲染。页面主要消费状态、发送操作，减少 500～700 行页面中同时处理规则、持久化与 UI 的耦合。

每次操作统一更新事件、历史游标和棋盘，再调度保存；保存任务按顺序执行，旧写入不能覆盖新状态。持久化使用无循环的数据结构，例如节点 ID 与父节点 ID；现有 `MoveTreeNode` 同时引用父节点和子节点，不宜直接整树交给 Gson 序列化。

第一阶段可以封装现有 SharedPreferences，先保证单槽存档正确。多棋局、检索和注释需求出现后，再评估 Room 等结构化存储。旧档迁移保留原数据备份，迁移失败仍允许用户保留或导出原局面。

### 7.2 AI 与界面响应

保留已经实现的 `Dispatchers.Default` 搜索和棋盘副本隔离。进一步为搜索加入会话标识、局面版本、模式和行棋方校验；重开、恢复、切换模式与进入摆谱时取消旧任务，提交结果前再次确认它仍属于当前局面。提示与 AI 对弈共用任务调度规则，避免重复搜索和过期高亮。

象棋与国际象棋的取消检查目前集中在根节点候选循环，应扩展到递归搜索和静态搜索的合适位置。加入迭代加深或等价的时间预算策略，超时返回最后一个已完成搜索的合法结果。界面可以显示等待状态、停止思考与可用操作，不显示无法估计的精确完成百分比。

### 7.3 发布质量

现有 CI 主要构建并发布 Debug APK，未把规则测试和交互测试作为发布门槛。建议增加规则、存储迁移、棋谱往返、AI 战术、核心 Compose 流程与 lint 检查；先完善这些检查，再发布正式 Release 构建。

当前 Debug 与 Release 共用仓库内签名材料。发布流程应明确签名材料的管理和已有用户的覆盖安装兼容方案；调整证书前验证升级与数据保留路径。版本文本、棋谱中的应用版本和更新说明统一读取构建信息。机器专属 JDK 路径改为本机配置，降低其他环境构建成本。
